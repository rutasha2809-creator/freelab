### Схема таблиц (актуально на 27.09.2026)

**`public.clients`** (владелец строки = `owner_id = auth.uid()`, RLS включён):
| Колонка | Тип | Смысл |
|---|---|---|
| id | uuid, PK | |
| owner_id | uuid | = auth.uid(), для RLS |
| name | text | Название клиента |
| type | text | `'recurring'` (Постоянный) \| `'oneoff'` (Разовый) |
| tasks_desc | text | Свободное описание задач по клиенту |
| plan_amount | numeric | Плановая сумма (или «аванс», если задан plan_amount2) |
| plan_day | int | День месяца платежа (1–31), для ежемесячных |
| plan_date | date | Ожидаемая дата — только для разовых (`type='oneoff'`) |
| plan_frequency | text | `'monthly'` \| `'weekly'`, только для recurring |
| plan_weekday | int | 1(пн)–7(вс), для еженедельных вместо plan_day |
| plan_amount2 | numeric | Сумма «остатка» при выплате 2 раза в месяц |
| plan_day2 | int | День выплаты остатка |
| contract_enabled | bool | «По договору» вкл/выкл |
| payer_type | text | `'individual'` (4% НПД) \| `'company'` (6% НПД) |
| created_at | timestamptz | |

Ограничения: `plan_frequency` — CHECK на два значения; `plan_weekday` — CHECK 1..7 или NULL.

**`public.payments`** (RLS по `owner_id = auth.uid()`, `on delete cascade` от clients):
| Колонка | Тип | Смысл |
|---|---|---|
| id | uuid, PK | |
| owner_id | uuid | |
| client_id | uuid | FK → clients.id |
| task | text | Название/тип платежа: `'Плановый платёж'`, `'Аванс'`, `'Остаток'`, `'Еженедельный платёж'` (для автосозданных) или произвольный текст (для вручную добавленных) |
| amount | numeric | |
| plan_date | date | Ожидаемая дата |
| fact_date | date, nullable | Фактическая дата получения; NULL = ещё не оплачено |
| auto_generated | bool | true — создано автоматически логикой графика (см. п.5); false — добавлено вручную |

Уникальное ограничение: `payments_client_date_task_auto_unique UNIQUE (client_id, plan_date, task, auto_generated)`

Ключи Supabase (anon/publishable) захардкожены в начале `js/app.js` — это нормально,
это публичный anon-ключ, доступ к данным ограничивается RLS-политиками на уровне БД,
а не секретностью этого ключа.

## 4. Как устроен код (js/app.js)

- Подключение: `sb = window.supabase.createClient(SUPABASE_URL, SUPABASE_ANON_KEY)` (CDN `@supabase/supabase-js@2`).
- Авторизация: email/password, экран `#authScreen` / приложение `#app`. Показ/скрытие
  через нативный атрибут `hidden` — см. критичный CSS-фикс ниже.
- `fetchState()` — единственная точка загрузки данных с сервера (clients + payments),
  вызывается один раз на пользователя из `showApp()` (есть защита `loadedForUserId`,
  чтобы повторные события Supabase Auth — обновление токена и т.п. — не запускали
  повторную загрузку и не плодили дубликаты, см. п.6).
- Маппинг camelCase (JS) ↔ snake_case (БД): `rowToClient`/`clientToRow`,
  `rowToPayment`/`paymentToRow`.
- `state = { clients: [], payments: [] }` — единственный источник истины в памяти,
  всё остальное — производные функции рендера от него.

## 5. Автоматический график платежей — как это работает

Раньше поля «день платежа» в карточке клиента были чисто справочными (только текст
в списке клиентов) — реальные платежи нужно было создавать вручную. Наталия попросила
автоматизировать: **приложение само генерирует ожидаемые платежи на 6 месяцев вперёд**
по данным карточки клиента, ей остаётся только отмечать факт оплаты.

Ключевые функции в `js/app.js`:
- `computeScheduledOccurrences(client, fromISO, toISO)` — считает даты и суммы
  ожидаемых платежей клиента в диапазоне (учитывает monthly/weekly, аванс+остаток,
  «прилипание» дня к последнему дню месяца, если день не существует, напр. 31 в феврале).
- `syncClientSchedule(client)` — сверяет уже существующие `payments` (где
  `auto_generated = true`) с тем, что должно быть по графику на горизонт
  `SCHEDULE_HORIZON_MONTHS = 6` месяцев вперёд, и **добавляет только недостающее**
  через `upsert(..., { onConflict: 'client_id,plan_date,task,auto_generated',
  ignoreDuplicates: true })` — защита от дублей на уровне БД (см. уникальное
  ограничение из п.3).
- `syncAllSchedules()` — вызывается один раз при каждой загрузке данных
  (`fetchState()`), «дотягивает» график по мере того, как проходит время
  (rolling horizon).
- `clearFutureAutoPayments(clientId)` — при редактировании карточки клиента удаляет
  ещё не наступившие и не оплаченные автосозданные платежи (`auto_generated=true AND
  fact_date IS NULL AND plan_date >= сегодня`), после чего `syncClientSchedule`
  строит новый график по обновлённым условиям. Оплаченные и добавленные вручную
  записи эта функция никогда не трогает.
- Список платежей на дашборде (`renderLists` → `renderGroupedPayments`) сгруппирован
  по месяцам в хронологическом порядке (ближайший месяц — сначала), с суммой за
  месяц в заголовке группы (см. классы `.monthGroup*` в `styles.css`).

Подписи автосозданных платежей (согласованы с Наталией, менять формулировки только
после её подтверждения — см. п.7): «Плановый платёж» (обычный ежемесячный),
«Аванс» / «Остаток» (сплит-платёж), «Еженедельный платёж».

## 6. Публикация изменений — пошаговый процесс

У ИИ **нет git push credentials** в этой среде (осознанное ограничение окружения) —
`git push` из `device_bash` всегда упадёт с `fatal: could not read Username for
'https://github.com'`. Поэтому процесс такой:

1. Отредактировать файлы локально в рабочей папке сессии
   (`/mnt/user-data/outputs/freelab/...`).
2. Если менялась структура БД — выполнить миграцию самому через
   `mcp__Supabase__apply_migration` (см. п.3). Наталию об этом не просить.
3. **Если менялся `index.html`** — обязательно поднять номер версии в
   cache-busting query-параметрах:
   `css/styles.css?v=N` и `js/app.js?v=N` — **на единицу для каждого изменённого
   файла** (GitHub Pages кеширует файлы ~10 минут, без этого браузер не увидит
   изменения). Текущие версии проверять по `index.html`, не считать «в уме».
4. Записать файлы на диск пользователя через
   `mcp__remote-devices__device_commit_files` (`devicePath: "~/mnt/FREELAB/..."`).
5. **ОБЯЗАТЕЛЬНО подождать 5–10 секунд и проверить через `device_bash`
   (`grep`/`cat`), что содержимое реально обновилось на диске** — синхронизация
   OneDrive иногда репортит успех раньше, чем файл физически долетает до диска.
   Если содержимое всё ещё старое — повторить запись (можно с `force: true`) и
   проверить снова. Не сообщать пользователю, что всё готово, пока это не
   подтверждено.
6. Закоммитить изменения локально через `device_bash`:
   `cd "$HOME/mnt/FREELAB" && git add -A && git commit -m "..."`.
   Предупреждения про `LF will be replaced by CRLF` — безобидны, это Windows-специфика
   git, игнорировать.
7. **Явно сказать Наталии**, что можно (или нельзя — если, например, миграция ещё не
   применена) запускать `ОБНОВИТЬ САЙТ.bat`. Она не должна сама гадать, безопасно ли
   обновлять — это её явное требование (см. п.7).
8. После того как она подтвердит запуск `.bat`, при необходимости проверить, что код
   реально дошёл до GitHub (`curl https://raw.githubusercontent.com/rutasha2809-creator/freelab/main/...`)
   и/или до самого сайта.
9. Сказать ей нажать Ctrl+F5 при первом открытии после обновления.

## 8. Известные грабли (уже наступали, чтобы не повторять)

- **Задержка синхронизации OneDrive.** `device_commit_files` может вернуть
  `"written"` до того, как файл реально долетит до диска. Всегда проверять `sleep` +
  `grep` после записи, как описано в п.6.4.
- **Забытый cache-busting.** Если поднять версию только у одного из двух файлов
  (`app.js`/`styles.css`) при изменении обоих — второй отдастся из кеша браузера.
  Поднимать версию у каждого изменённого файла.
- **CSS-специфичность `[hidden]`.** Была системная проблема: атрибут `[hidden]` со
  стандартным `display: none` из UA-стиля проигрывал по специфичности любому
  авторскому классу с `display` на том же элементе (`.app`, `.field`, `.field-row`
  и т.п.), из-за чего «скрытые» элементы оставались видимыми (баг с не скрывающимся
  экраном входа, незакрывающимися полями формы). Исправлено один раз глобально в
  начале `styles.css`:
  ```css
  [hidden] { display: none !important; }
  ```
  Если где-то снова «элемент не скрывается, хотя `hidden` стоит» — сначала
  проверить, не завёлся ли новый конфликтующий `display`-селектор, а не чинить
  точечно.
- **Гонка при входе → дубли автоплатежей.** `onAuthStateChange` и
  `sb.auth.getSession().then(...)` оба могли вызвать `showApp()` → `fetchState()`
  почти одновременно, из-за чего `syncClientSchedule` запускался несколько раз
  параллельно и создавал дубли одинаковых автоплатежей (было замечено — 3 копии
  каждого). Исправлено: (а) флаг `loadedForUserId` не даёт загружать данные повторно
  для того же пользователя, (б) уникальное ограничение в БД +
  `upsert(..., ignoreDuplicates: true)` не даёт создать дубль, даже если что-то
  подобное произойдёт снова.
- **Не путать «карточка клиента» и «платежи».** Поля дня/периодичности в карточке
  клиента — это входные данные для генератора графика (п.5), сами по себе они не
  являются платежами. Реальные записи о деньгах — это строки в `payments`.

## 9. Хронология ключевых решений (кратко, от старого к новому)

1. Миграция хранения с localStorage браузера на Supabase (сайт стал публичным).
2. Добавлена авторизация Supabase Auth (email/пароль, восстановление пароля).
3. Найден и исправлен системный баг с `[hidden]` (см. п.8).
4. Добавлена возможность «выплата двумя частями в месяц» (аванс + остаток) —
   `plan_amount2`/`plan_day2`.
5. Добавлена периодичность «еженедельно» как подвид «Постоянного» клиента (не
   отдельный тип/вкладка) — `plan_frequency`/`plan_weekday`.
6. Подключён MCP-коннектор Supabase — с этого момента ИИ сам вносит изменения в БД,
   Наталии больше не нужно выполнять SQL руками.
7. Добавлена автоматическая генерация графика ожидаемых платежей на 6 месяцев вперёд
   по данным карточки клиента (п.5 выше).
8. Найдена и исправлена гонка, создававшая тройные дубли автоплатежей; список платежей
   переделан в таблицу, сгруппированную по месяцам с суммами (п.8 выше).

## 10. Что можно улучшить дальше (не срочно, не начинать без запроса)

- Сплит-платёж (аванс+остаток) сейчас поддержан только для ежемесячных клиентов —
  для еженедельных такой комбинации нет (осознанно скрыто в UI).
- Список платежей группируется по месяцам целиком за всю историю — если со временем
  накопится много оплаченной истории, возможно, стоит добавить фильтр/сворачивание
  прошлых месяцев.
- Нет ручной кнопки «пересобрать график» — пересборка происходит только при
  редактировании карточки клиента или при открытии приложения.
